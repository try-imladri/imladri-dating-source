This directory fingerprints retained signed vendor libraries. It does not contain a custom glibc build or close a vulnerability case.

Wolfi glibc 2.44-r17 is an ordinary signed package update. Its main APK, loader APK, embedded recipes, immutable upstream source archive, authenticated installation proof and repository-index linkage are recorded in `facts.json`. All 19 regular ELF files from these two APKs match the separately authenticated vendor root, including the loader and `/usr/bin/ldconfig`. The runtime inventory producer checks their actual installed bytes and exact APK package/version/control identities. The component artifact checksum identifies the main glibc APK; the separately hashed loader APK is also a mandatory verified input. The held custom glibc bundles are absent from these release inputs.

SQLite 3.54.1-r0 and ncurses 6.6.20261107-r0 retain their previously reviewed signed APK bytes. Their source archives, embedded recipe checksums and 28 installed ELF/alias rows are pinned. APK authenticity is established through the repository index accepted by APK with its existing trusted keys, followed by exact control-checksum and payload-datahash comparisons. No standalone APK signature claim is made.

`build_native_inventory.py` rehashes every referenced local input, every declared installed native file, all native symlink targets and the installed APK identities before writing a new fixed manifest. Unknown package revisions or file bytes fail even when the other check still matches. Source/artifact hashes describe the producer chain; runtime verification measures installed and mapped native bytes. A staged byte preflight is not an application boot or a provider release attestation.

All historical raw advisory cases and exposure decisions remain in their existing ledgers. The pinned SQLite source has independently matched all five primary production fix hunks for recursive CTE case CVE-2026-119371; an ordinary baseline check also measured the enabled expression-depth limit at 1000. Its source-fix evidence is recorded with the other source-matched SQLite cases, and actual new-release mapping verification is still required. In particular, the held glibc cases CVE-2026-100290 and CVE-2026-115819, disputed ncurses CVE-2021-45346, and separate SQLite CLI CVE-2026-119586 are not newly closed here. A component's empty `cases` list makes no claim that it has no vulnerabilities. Priority 1 was untouched.
